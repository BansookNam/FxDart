# 이 추상들이 치르는 값

> **이 장에서 다루는 것**
> - 실제 과제 53개에서 측정된 트레이드오프의 모양
> - 파이프라인을 느리게 만드는 두 가지 장치와 빠르게 만드는 한 가지
> - 왜 여기서 거의 모든 성능 질문의 답이 "할당"인가
> - 남의 비율을 믿지 않고 여러분의 코드에서 판단하는 법

## 숫자

FxDart는 나란히 비교하는 예제 53개 각각을, 같은 과제를 손으로 쓴 Dart 버전과
비교하는 벤치마크 스위트를 싣습니다. AOT 컴파일, 반복 측정의 중앙값입니다.
각 케이스의 가장 큰 스케일에서:

| 대표 스케일에서의 결과 | 케이스 수 |
|---|---|
| 무승부 (5% 또는 0.6ms 이내) | 13 |
| 손으로 쓴 Dart가 더 빠름 | 19 |
| FxDart가 더 빠름 | 21 |

53개 전체의 중앙값 비율은 **1.01×** — 대체로 비긴 셈이고, 케이스가 양쪽에
거의 반반씩 갈리며 그중 4분의 1은 잡음 구간 안에 있습니다.

중앙값보다 흥미로운 것은 양극단입니다.

| 케이스 | 비율 | 의미 |
|---|---|---|
| `restock-plan` | **0.24×** | 파이프라인이 4배 넘게 *빠름* |
| `top-expenses` | 0.38× | 파이프라인이 2.6배 빠름 |
| `consecutive-over-limit` | 1.19× | 파이프라인이 1.2배 느림 |
| `recent-errors` | **1.32×** | 파이프라인이 1.3배 느림 |

같은 라이브러리, 같은 기계, 최고와 최악 사이에 다섯 배 차이. 그러므로
"Dart에서 FP는 *n*배 느리다" 형태의 문장은 전부 거짓입니다. 그 수는 아래 세 장치
중 무엇이 지배하느냐에 전적으로 달려 있습니다.

## 장치 1 — 원소당 간접성 (비용)

손으로 쓴 루프는 원소를 읽고 여러분의 코드를 인라인으로 적용합니다. 파이프라인은
모든 원소를 단계마다 이터레이터에 통과시킵니다. 가상 `moveNext`, `current` 게터,
클로저 호출. Dart의 AOT 컴파일러가 그중 상당수를 인라인하지만 다형적 이터레이터
경계를 넘어서는 인라인하지 못하고, 그 비용은 *원소마다, 단계마다* 지불됩니다.

위 표의 패배자들이 균일한 데이터 위에 값싼 단계가 많은 예제인 이유가
그것입니다. 필터 뒤에 중복 제거가 이어지는 체인, 슬라이딩 윈도 비교, 작은 수치 계산. 원소당
오버헤드는 고정인데 원소당 유용한 일은 아주 작으니 비율이 나빠집니다. 그런데 그
"나쁨"이 얼마나 나쁜지 보세요. 스위트에서 가장 느린 케이스가 1.3배이지 10배가
아닙니다.

```dart run
import 'package:fxdart/fxdart.dart';

void main() {
  final data = List.generate(200000, (i) => i);
  final sw = Stopwatch()..start();

  var loop = 0;
  for (final n in data) {
    if (n.isEven) loop += n * 2;
  }
  final loopMs = sw.elapsedMicroseconds;

  sw.reset();
  final piped =
      fx(data).filter((n) => n.isEven).map((n) => n * 2).sum();
  final pipeMs = sw.elapsedMicroseconds;

  print([loop, piped, loop == piped]);
  print('loop ${loopMs}us, pipeline ${pipeMs}us');
  // In the browser this is JIT-compiled JS, so treat the ratio
  // as indicative; the book's table is AOT.
}
```

## 장치 2 — 할당 (양쪽에, 다르게)

스위트에서 나타나는 큰 차이 대부분은 CPU 연산이 아니라 가비지(할당된 메모리)에서 나옵니다. 그룹핑 과제의
손으로 쓴 버전은 중간 `List`와 `Map`을 만들고, 파이프라인 버전은 하나도 안 만들
수도, 원소마다 레코드를 만들 수도 있습니다. 어느 쪽이 더 많이 할당하는지는
과제에 달렸고, 그것이 다르면 할당이 측정 시간을 지배합니다. 관련된 또 하나의
지렛대는 이름 붙은 단계 뒤의 구현입니다. 라이브러리의 `sortBy`나 `foldBy`는 타입이
정해진 버퍼와 한 번의 패스로 한 번만 작성해 두면 되지만, 손으로 쓴 버전은 매번
같은 것을 범용 부품으로 다시 조립합니다.

이것이 가장 쓸모 있는 진단입니다. *양쪽의 할당을 세어 보세요.* 같다면 두 버전은
잡음 범위 안에서 서로 비슷합니다. 한쪽이 다른 쪽은 만들지 않는 중간 컬렉션을
구체화한다면, 그쪽 루프가 아무리 촘촘해도 집니다.

## 장치 3 — 거부한 일 (이득)

11장의 비용 모델이 점수판에 나타난 것입니다. 다만 기대만큼 자주는 아닙니다.
과제가 "이 데이터의 대부분은 상관없다"는 모양일 때, 지연 평가 덕분에
파이프라인은 필요한 만큼만 가져오고 멈출 수 있습니다. 백만 개에서 처음 유효한
주소 다섯 개를 원하는 `valid-emails`가 그런 경우인데, 이득은 겨우 8% 정도입니다.
신중하게 쓴 손 루프도 일찍 멈추기 때문입니다. 지연 평가가 큰 승리를 안겨 주는
것은 네이티브 쪽이 일찍 멈추지 *않을* 때뿐입니다. 일찍 멈추는 손 루프를 상대로는
거부한 일이 절약한 원소당 오버헤드만큼으로 줄어듭니다.

큰 승리를 무엇의 공으로 돌릴지 조심하세요. `top-expenses`(0.38×)는 끝에 `take(3)`이
있어서 지연 평가처럼 보이지만, `sortBy`는 즉시 평가입니다. 양쪽 모두 백만 행을
전부 정렬합니다. FxDart가 이기는 이유는 `sortBy`가 각 키를 한 번만 뽑아 타입이
정해진 배열에 담아 병합하는 반면, 네이티브 `sortedBy`는 비교할 때마다 키 함수를
호출하기 때문입니다. 이것은 장치 2의 사촌(단계당 더 값싼 구현)이지 거부한 일이
아닙니다. 이 스위트에서 FxDart의 가장 큰 승리들(`restock-plan`, `top-expenses`,
`top-log-level`)은 이런 종류이니, 큰 비율을 지연 평가가 보답했다는 증거로 읽지
마세요.

![비율은 어디서 오는가](diagrams/t14-1-cost-shape.svg)

*그림 14-1. 서로 독립인 세 힘. 간접성은 원소마다, 단계마다 붙는 고정 세금이고, 할당은 중간물을 더 많이 만드는 쪽이 치르는 비용이며, 거부한 일은 종결 연산자가 일찍 멈출 때 파이프라인이 받는 환급이다.*

## 이것을 정직하게 유지하는 측정 규칙

스위트 자신의 규칙이고, 베껴 둘 만합니다.

- **JIT이 아니라 AOT.** JIT 수치는 워밍업이 잘 되는 쪽이 유리하게 나옵니다.
- **새 프로세스에서 반복 측정한 중앙값**, 한 번 잰 값이 아니라.
- **무승부 구간** — 5% 또는 0.6ms — 사용자가 지각할 수 없는 차이는 차이가
  아니니까요. 53개 케이스 중 13개가 여기 들어옵니다.
- **메모리도 보고할 것.** 최대 RSS에는 중간 리스트가 드러나며, 작은
  컨테이너에 이 작업이 들어가는지를 결정하는 숫자입니다.
- **두 번 돌려 보지 않은 주장은 절대 벤치마크로 쓰지 말 것.** 조용한 기계에서도
  실행 간 잡음이 5% 정도이므로, 한 번 재서 나온 한 자릿수 퍼센트 차이는 동전
  던지기입니다.

> 🎓 **빅오는 그대로지만 상수는 그렇지 않습니다.** 위의 어떤 것도 점근 복잡도를 바꾸지
> 않습니다. 지연 `filter` + `map` + `fold`는 루프와 똑같이 O(n)이고,
> `top-expenses`는 양쪽 모두 O(n log n) 정렬을 하는데도 빠릅니다. 개선된 것은
> 알고리즘이 아니라 상수입니다. 큰 승리를 발견하면 둘 중 무엇이었는지
> 물으세요. 상수 배수 승리는 튜닝 결과이고, 점근적 승리(입력 대부분을 건너뛰는
> 조기 종료)는 설계 결과이며, 입력 크기가 바뀌어도 살아남는 것은 후자뿐입니다.

## 여러분의 코드에서 판단하는 법

1. **일단 무승부라고 가정하세요.** 스위트 자체의 집계에서 중앙값이 1.01×이고,
   그러면 남는 기준은 읽기 쉬움뿐입니다.
2. **거부한 일을 찾으세요.** 큰 소스에 대한 `take`, `first`, `find`, 또는 일찍
   빠져나가는 `any`는 파이프라인이 이길 것이라 기대할 이유입니다. 단, 대신 쓸 루프가
   마찬가지로 일찍 멈추지 않는다면 말이죠.
3. **중간물을 찾으세요.** 양쪽에서 세어 보고, 많은 쪽이 집니다.
4. **실제 케이스를 두 번 측정하세요.** 무승부 구간을 염두에 두고, AOT로, 프로그램이
   실제로 만나는 크기에서.
5. **그런 다음 고르세요.** 최악의 경우 1.3×는 팀이 읽을 수 있는 코드에 대한
   공정한 값이고 — 프레임 렌더러의 안쪽 루프에서 치를 값은 아닙니다.

## 언제 루프를 꺼내 들 것인가

핫 패스이고, 단계가 값싸고, 소스가 전부 소비될 때 `for` 루프를 쓰세요. 정확히
지는 모양입니다. 연산이 정말 명령형일 때도 루프를 씁니다. 버퍼 변경, 크기가 정해진
리스트 채우기, 인덱스 기반 알고리즘 돌리기. 나머지 경우들은 22장이 모아 두었고,
이 장의 기여는 이제 여러분이 짐작 대신 답을 *예측*할 수 있고 10분 만에 확인할 수
있다는 것입니다.

## 연습문제

1. 원소 100만 개에 단계가 다섯이고 `.first`로 끝나는 파이프라인이 있습니다. 세
   장치 중 무엇이 지배하고, 같은 일을 하는 루프 대비 예상 비율은 얼마인가요?
2. 그룹핑 과제의 두 버전을 비교할 때 왜 최대 RSS가 경과 시간보다 나은 판별
   기준인 경우가 많은가요?
3. 스위트는 5% 미만 차이를 무승부로 칩니다. 4% 차이가 진짜로 중요한 경우를
   구성하고, 그것을 신뢰성 있게 검출하려면 측정에서 무엇을 바꿔야 하는지
   말하세요.
4. `consecutive-over-limit`(인접한 측정값 셋이 한도 초과)은 파이프라인이 약 1.2배
   느립니다. 코드를 보기 전에, 이
   장을 근거로 그 원인이 될 과제의 두 특징을 예측하세요.

## 정답과 해설

1. 거부한 일이 지배합니다. `.first`는 원소 하나를 다섯 단계에 통과시키므로
   파이프라인이 하는 일은 대략 클로저 호출 다섯 번인 반면, 루프 버전은 —
   순진하게 썼다면 — 리스트 전체를 처리합니다. 예상 비율은 엄청나며 파이프라인
   쪽이 유리합니다. 루프도 일찍 빠져나온다면 둘은 무승부에 파이프라인의 고정
   단계 오버헤드를 더한 값으로 수렴합니다.
2. 그룹핑이야말로 중간물이 숨는 자리이기 때문입니다. 메모리가 넉넉하고 워밍업이 끝난
   기계에서는 두 버전의 시간이 같게 나올 수 있는데, 한쪽은 모든 그룹을 한꺼번에
   메모리에 들고 있고 다른 쪽은 흘려보냅니다. RSS는 그 차이를 즉시 보여 주고, 더
   큰 입력에서 어느 쪽이 무너질지 예측합니다.
3. 120fps로 도는 렌더 루프의 예산은 8.3ms이므로, 5ms 프레임의 4%는 약 3분의 1ms의
   여유입니다 — 진짜죠. 그것을 검출하려면 측정 한 번당 반복 횟수를 훨씬 늘리고
   (타이머 해상도 위로 신호를 올려야 합니다), 기계를 조용히 하고, 차례로가 아니라
   짝지어 번갈아 A/B를 돌려야 합니다. 그래야 드리프트가 양쪽에 똑같이 걸립니다.
4. 균일한 수치 데이터 위의 값싼 단계 여럿(슬라이딩 윈도 + 비교 + map)에, 전부
   소비됨 — 어떤 단계도 일을 거부하지 않으며, 원소마다 여러 번 치르는 간접성을
   상쇄할 실제 계산은 거의 없습니다.
